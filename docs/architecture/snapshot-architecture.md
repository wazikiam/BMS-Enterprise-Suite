\# BMS Enterprise Suite — Snapshot Architecture (Authoritative)



\## 1. Purpose



This document defines the final, frozen architecture for snapshot handling in BMS Enterprise Suite.



It establishes:

\- System boundaries

\- Authority ownership

\- Data lifecycle rules

\- Failure semantics



This document is authoritative. Behavior described here is intentional, not incidental.

\## 3. Authority Model (Separation of Duties)



\### 3.1 UI — Governance Authority

The UI is the \*\*sole authority\*\* for:

\- Snapshot sealing

\- Verification

\- Approval (4-eyes principle)



Governance metadata:

\- Is stored locally (UI-controlled)

\- Must survive server restarts

\- Is never recomputed by backend services



The backend \*\*does not reinterpret governance state\*\*.



---



\### 3.2 Server — Enforcement Authority

The server enforces:

\- Cryptographic integrity

\- Role-based access control

\- Explicitness of restore and apply actions

\- Append-only audit logging



The server does not:

\- Auto-restore

\- Auto-apply

\- Invent payloads

\- Repair missing runtime state



---



\### 3.3 Audit Vault — Payload Authority

The Audit Vault is authoritative for:

\- Sealed snapshot payloads

\- Integrity verification

\- Restore/apply event history



Properties:

\- Content-addressed by sealedHash

\- Write-once per hash

\- Append-only event log

\- Immutable by design



Presence in the vault does NOT imply runtime availability.



---



\### 3.4 Runtime Snapshot Store — Convenience Layer

The runtime snapshot store exists only to:

\- Serve snapshot payloads for viewing



Properties:

\- Non-authoritative

\- May be in-memory

\- May be cleared on restart

\- Absence is an expected, valid state



---



\## 4. Snapshot Lifecycle



\### 4.1 Generation

\- Snapshot payload is generated by server/core logic.

\- Payload exists in runtime only.



\### 4.2 Governance

\- UI seals payload (hash computed).

\- UI verifies and approves snapshot.

\- Approval metadata is stored locally.



\### 4.3 Vault Persistence (Explicit)

\- UI calls `/vault/store`.

\- Server recomputes hash and verifies integrity.

\- Payload is written immutably to vault.



\### 4.4 Runtime Loss (Expected)

\- Server restart may clear runtime payload.

\- Approved snapshot may now return 404.

\- This is correct behavior.



\### 4.5 Explicit Recovery

\- Operator checks `/vault/status`.

\- Operator calls `/vault/restore` (intent logged).

\- Operator calls `/vault/apply` (activation logged).

\- Runtime payload becomes available again.



---



\## 5. Failure Semantics (Intentional)



| Scenario | Result | Reason |

|--------|--------|--------|

| Approved snapshot, runtime missing | 404 | Runtime is non-authoritative |

| Vault missing | 404 | No audit payload exists |

| Hash mismatch | 409 | Integrity violation |

| Restart clears runtime | Allowed | By design |

| Restore without apply | No runtime | Restore ≠ activation |



No silent repair exists in this system.



---



\## 6. Design Guarantees



This architecture guarantees:

\- No governance drift

\- No hidden state repair

\- No audit ambiguity

\- Deterministic behavior under failure

\- Clear separation of power



---



\## 7. Explicit Non-Goals



The system explicitly does NOT:

\- Guarantee runtime persistence

\- Auto-heal missing payloads

\- Recompute approvals

\- Optimize for convenience over correctness



These are intentional exclusions.



---



\## 8. Final Statement



If an approved snapshot cannot be rendered, it is not a bug.

It is an honest reflection of system state.



Correctness is preferred over convenience.
